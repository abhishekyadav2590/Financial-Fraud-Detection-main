# Research readiness

## Scope and intended use

FinShield AI is a Flask demonstration of a financial-transaction fraud-risk workflow. Its current classifier is trained on generated educational data. The project is suitable for software and methodology demonstrations, not for estimating real-world fraud prevalence or making decisions about real people or transactions.

The central research limitation is the target-generation process: `dataset/transactions.csv` is generated by `generate_dataset.py`, whose synthetic fraud labels are sampled from a hand-authored probability function of the same kinds of transaction features supplied to the model. Results therefore measure how a fitted model behaves on this simulated process; they do not establish that the generated patterns represent real fraud.

## Verified dataset and model facts

| Item | Repository evidence |
|---|---|
| Dataset | `dataset/transactions.csv`, reproducible generator seed 42 |
| Rows and labels | 20,000 rows; 989 synthetic positive labels and 19,011 synthetic genuine labels (4.945% positive) |
| Inputs | 10 transaction features; `transaction_id` is excluded from training |
| Model | Saved scikit-learn preprocessing/classification pipeline; selected classifier is Logistic Regression |
| Selection split | Stratified 60% train / 20% validation / 20% held-out test; fixed random state 42 |
| Threshold | `0.1484438619`, selected using validation data; separate display bands are LOW below 0.10, MEDIUM below 0.30, and HIGH otherwise |
| Final artifact | After measuring the selected pipeline on the held-out split, the training script refits the selected configuration on all 20,000 rows and saves that final pipeline |

The held-out metrics recorded in `model/model_metadata.json` and `model/ml_evaluation_report.json` are from the selected model **before** the final all-data refit:

| Metric | Recorded held-out result |
|---|---:|
| Accuracy | 0.918 |
| Precision | 0.2421 |
| Recall | 0.3081 |
| F1 | 0.2711 |
| ROC AUC | 0.7255 |
| PR AUC | 0.1880 |

| False-positive rate | 0.0502 |

These are synthetic hold-out results, not estimates of real deployment performance. The recorded false-negative rate and precision make clear that the current threshold/classifier misses many generated positive cases and flags many negatives. Accuracy alone is particularly insufficient to characterize this imbalanced task. The synthetic positive prevalence (4.945%) is a useful reference point when interpreting precision-recall results, not a substitute for a defined operational baseline.

## Research questions to investigate

These are proposed questions, not established findings:

1. How do precision, recall, PR AUC, ROC AUC, Brier score, and confusion-matrix counts change across validation-selected thresholds on this generated process?
2. How stable are those metrics across repeated generator seeds and independently generated hold-out samples?
3. How does the selected Logistic Regression pipeline compare with simple, documented baselines under the same split and threshold-selection protocol?
4. Are predicted probabilities calibrated on held-out synthetic data, and how sensitive are calibration and error rates to the generator's class prevalence and feature distributions?
5. Which features drive the model's predictions, and do the explanations remain stable under controlled changes to the synthetic generator?

Any subgroup or fairness analysis requires suitable, lawfully obtained, documented attributes and a justified study design. The current feature set does not establish demographic fairness and should not be used to claim it.

## Research-paper and synopsis integrity

The project folder contains PDF copies of a paper, a synopsis, and similarity/AI-detection reports, but no editable source documents or independent verification data. This project cannot guarantee a detector score, and detector results are not proof of authorship or plagiarism. Do not rewrite work to evade a detector or target a particular similarity percentage. Instead, write from the actual experiment and your own understanding, cite borrowed ideas and wording, quote when exact wording is necessary, verify every reference, distinguish proposed work from completed results, and follow your institution's disclosure and authorship rules for AI-assisted work. Keep drafts, source notes, experiment logs, and version history so the research process is transparent.

For accuracy, any new paper or synopsis should clearly state that the classifier was trained on synthetic generated labels, report results from the stated evaluation split without implying real-world validation, and avoid presenting account-statement anomaly scores as model predictions or confirmed fraud. The two account-statement PDFs are private exploratory inputs; without independently verified fraud outcomes and consent/provenance documentation, they are not labeled training data and must not be used to claim model performance.

The supplied October statement filename indicates that a page was removed. Its parsed rows therefore represent only the supplied PDF, not a verified complete account history; do not make completeness or longitudinal-behavior claims from it until the source owner confirms the missing-page context.

## Recommended study protocol

1. Preserve the current model, dataset, metadata, evaluation report, and evaluation artifacts. Conduct experiments in a separate copy or use versioned experiment outputs so the delivered artifacts remain unchanged.
2. Write down the research question, target population, outcome definition, sampling process, comparison baselines, primary metric, threshold-selection rule, and exclusion criteria before examining results.
3. Keep all fitted preprocessing inside the scikit-learn pipeline and fit it only on training data. Choose hyperparameters and thresholds on validation data. Use the held-out test set once for the final comparison.
4. Because this generated dataset is independently sampled rather than a real event stream, also evaluate repeated seeds. If a suitable real-world dataset is later approved, prefer time-aware evaluation where it reflects the intended deployment and prevent entity/time leakage.
5. Report class prevalence, confusion matrices, precision/recall, PR AUC, ROC AUC, probability calibration, uncertainty intervals, and threshold-specific tradeoffs. State which data split each result comes from.
6. Separate model predictions from analyst-confirmed outcomes. The current review statuses (`PENDING`, `REVIEWED`, `ESCALATED`, `CLEARED`) are workflow states, not verified fraud labels.
7. Document data provenance, synthetic label construction, feature definitions, missingness, constraints, privacy/consent, and limitations. Do not upload financial records or secrets to public research tools.
8. Treat coefficients and counterfactuals as model behavior explanations, not causal explanations or proof of fraud.

## Suggested report structure

1. Abstract and research question
2. Background and related work
3. Data source, synthetic generator, target construction, and limitations
4. Preprocessing, split design, model, baselines, threshold selection, and metrics
5. Results by split and threshold, including confusion matrices and precision-recall analysis
6. Error analysis, calibration, robustness, and explanation stability
7. Ethical, privacy, fairness, and human-review considerations
8. Limitations and future work
9. Reproducibility appendix with code revision, dependency environment, random seeds, and artifact hashes

## Reproducibility and preservation warning

The training scripts are reproducibility tools, not harmless read-only checks. `generate_dataset.py` overwrites `dataset/transactions.csv`; `train_final_model.py` writes the saved model, metadata, and evaluation artifacts. Before running either command, work in a separate project copy and preserve the original files. The latest local verification completed all 18 test suites; those tests do not validate real-world model performance.
